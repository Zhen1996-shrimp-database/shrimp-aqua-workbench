对虾养殖产业数据库工作台 —— 技术实现方案

目标：打通"中英文文献检索 → 自动解析 → 结构化抽取 → 数据治理 → 季度增量合并"全链路，构建可复用、可审计、可持续运营的对虾养殖产业数据中台。

适配基础：基于现有的《对虾养殖产业数据库2.xlsx》（11 个工作表，1300+ 行存量记录）做增量扩展与统一治理。

1. 总体技术架构

1.1 设计原则

原则 说明
存算分离 原始 PDF/HTML 入对象存储（元数据入库），解析结果入结构化库，计算节点无状态
人机协同 AI 抽取 + 人工校验的关键卡点（"人确认"环节）必须由工作流强制
可观测 每条数据记录可追溯到原文页码 / 表格编号 / 抽取 prompt 版本
可扩展 新增数据源/字段时只需新增 Adapter / Field，无需重构流水线
合规优先 严格遵守各数据库 robots 与版权条款，仅采集公开摘要与授权全文

3. 解析与 ETL 流程设计

3.1 全链路流水线（13 步）

┌──────────────────────────────────────────────────────────────┐
│  Step 1  检索查询生成         QueryBuilder                   │
│  Step 2  多源并发抓取         SourceAdapter (async)          │
│  Step 3  元数据归一化         MetadataNormalizer             │
│  Step 4  全文获取             Fetcher (PDF/HTML/XML, 301重试) │
│  Step 5  文件落地             MinIO / S3                     │
│  Step 6  文档解析 Layout      PyMuPDF + pdfplumber + Tika     │
│  Step 7  表格/数值定位        TableExtractor (CAMERO/版面分析)│
│  Step 8  候选字段粗筛         NumericPreFilter (regex+slot)  │
│  Step 9  LLM 语义抽取         FieldExtractor (GPT-4/Claude) │
│  Step 10 规则后置校验         RuleValidator                  │
│  Step 11 单位换算+标准化      UnitNormalizer                 │
│  Step 12 字段存草稿表         DraftStorage                   │
│  Step 13 人工审核→写入主表    ReviewQueue + MergeService     │
└──────────────────────────────────────────────────────────────┘

3.2 Step 6：文档解析双引擎

引擎 用途 关键能力
PyMuPDF (fitz) 学术 PDF 默认首选项 快、坐标精确、表格框选
pdfplumber 二维表格抽取 行列识别 + 字符级重排
Apache Tika 兜底 万能格式归一化（DOCX/HTML/EPUB）
PaddleOCR / Marker 扫描件 OCR 旧规范、政府公文、JPG 表格图片

输出统一为 Docling Common Format（每页含 blocks, tables, figures, refs）。

3.3 Step 7-9：字段抽取 = "规则 + LLM" 双通道

通道 A：规则抽取（首选）

针对高频模板的论文（中国海洋大学博论文 / 期刊固定栏目）： - 训练 CRF/正则匹配置信度 ≥ 0.9 时直接采纳。 - 例：r"存活率.*?(\d+(?:\.\d+)?)\s*%" - 例：r"饲料系数[为:为可低]?\s*(\d+(?:\.\d+)?)"

通道 B：LLM 抽取（兜底）

SYSTEM:
你是水产养殖数据抽取专家。每次给出 JSON，禁止输出解释。
抽取字段集合（schema 注入，禁止越界）：
  water_quality: {水温WT, pH, DO, 盐度, NH3-N, NO2-N, NO3-N, COD, TN, TP,
                  透明度, 总碱度, 钙离子}
  cost_items: {苗种, 饲料, 动保, 人工, 租金, 水电, 设备折旧}
  benefit: {单产, 总产, 产值, 净利润, 投入产出比, ROI, FCR, 成活率}
  meta: {养殖模式, 养殖周期, 放苗密度, 规格, 地域, 时间, 文献来源}

USER:
[原文片段 chunk N of M] (含页码/表格编号)
请输出 JSON。每个字段都给出 evidence_text 与 page_no。
找不到则留 null 并说明缺失原因。

约束：
- 数值必须与原文一致，禁止换算
- 含义不明时给 ""unknown""
- 单条记录只对应同一篇文献同一组数据
- 不要把单位写成数字的一部分

两通道融合规则： 1. 规则先跑；命中且置信度 > 0.9 → 直接采纳。 2. 未命中字段 → 调用 LLM。 3. LLM 抽取与规则一致 → 二者皆入库（投票机制）。 4. 二者冲突 → 进 L2 人工核验队列。

3.5 抽取失败兜底

  • 若文献无可用全文 → 仅入库"文献实体表"，不入数据表，标 fulltext=missing。
  • 若 OCR 失败 3 次 → 转人工 transcription queue。
  • 若 LLM 调用超时 / token 超限 → 分 chunk 重试 + 异步合并。

4. 重复文献去重机制

采用 "指纹 + 文本相似度" 三级漏斗，3 分钟内处理 1 万条记录。

4.1 三级去重漏斗

输入记录
   │
   ▼
Level 1 — DOI / PMID / CN号 精确匹配                命中 → 跳过
   │ 未命中
   ▼
Level 2 — 标题指纹（SimHash 64-bit / MinHash）      汉明距离 ≤ 3 → 提示合并
   │ 未命中
   ▼
Level 3 — 嵌入向量召回（pgvector, text-embedding-3-small）
          + 余弦阈值 0.93 → 进入人工合并决策          未命中 → 入新记录

4.2 Level 1 精确匹配

SELECT id FROM literature
WHERE doi = ?
   OR (pmid IS NOT NULL AND pmid = ?)
   OR (cn_no IS NOT NULL AND cn_no = ?);

4.3 Level 2 标题指纹

  • 预处理：去标点 → 转小写 → 去前后空格 → 中文用 jieba 分词 + 英文用 NLTK 词形还原。
  • Hash：SimHash 64bit（也可切 MinHash-128 用于候选召回）。
  • 命中：汉明距离 ≤ 3 或 Jaccard ≥ 0.85。

4.4 Level 3 嵌入向量

索引 推荐 维度
pgvector + HNSW 默认 1536
备选 Qdrant + IVF 大规模 1536 
CREATE TABLE lit_embedding (
  lit_id BIGINT PRIMARY KEY,
  embedding vector(1536) NOT NULL
);
CREATE INDEX lit_embedding_hnsw ON lit_embedding
USING hnsw (embedding vector_cosine_ops);

4.5 合并策略

情况 行为
同一文献在不同数据库（CNKI 与 WoS 各有一条） 合并为一条，由"主源"承载元数据，其他源写进 duplicate_of
同一数据集在不同期刊发表的姊妹篇 保留两条，标记 related_paper_of
同一数据被多次引用 每条抽取独立入库，文献实体的 cited_by_records 反查计数

5. 数据质量校验规则

5.1 校验规则引擎架构

采用 Great Expectations + Soda Core 双核：

  • GE：schema、强类型、范围、跨表一致性。
  • Soda：自定义业务规则（典型：成本占比合计 = 100%）。

所有规则代码入库 data-quality/rules/，rule-as-code，每次 ETL 自动跑。

5.2 12 类规则全景

# 类别 规则示例 失败处理
R01 完整性 必填字段非空：source_id, doi/title, literature_id, year 严重 → 拒收；非严重 → 进补全队列
R02 唯一性 literature_id 主键唯一；草稿表内 lit_id + section_no 唯一 拒收
R03 数值类型 WT, DO, pH 等必须是 float；不可夹杂单位字符串 解析前清洗
R04 范围 sanity check WT ∈ [5, 40]°C；DO ∈ [0, 20] mg/L；pH ∈ [5, 11]；盐度 ∈ [0, 50]‰；NH₃-N ∈ [0, 50] mg/L 警示 + 进人工核对
R05 逻辑一致性 放苗密度 × 养成规格 × 周期 → 总产应满足密度约束；溶解氧 < 0 时 FCR 必有显著偏高 警示
R06 比例约束 成本分项占比合计 = 100% ± 0.5%；若是± 5% 进差异队列 警示 + 重核
R07 单位一致 mg/L μg/L g/m³ 自动归一，单位跟随默认 自动换算
R08 货币时间归一 价格 → 2025 基准 CPI 折算；汇率取人民银行年中值 自动
R09 跨表交叉验证 水质表 vs 生长表：同一 lit_id + culture_mode 的 WT 偏差 > 3°C 必查 警示
R10 来源可追溯 每条抽取记录必含 evidence_text + page_no + extraction_prompt_ver 拒收
R11 经纬度一致性 同一地点经纬度偏差 > 0.2° → 提示；省份与经纬反查行政编码不一致则阻断 阻断
R12 可重复性 同一篇文献二次抽取结果差异 > 5% 字段 → 进配置巡检 提示

5.3 校验失败的分级处置

PASS            ─ 入主库 L1
WARN            ─ 入主库 L2（黄色标），触发邮件给数据管理员
BLOCKED         ─ 仅入草稿 + Review 队列，需人工确认
CRITICAL        ─ 自动告警到飞书/钉钉群 + 创建 Jira

  region_city        TEXT,
  latitude           NUMERIC(9,6),
  longitude          NUMERIC(9,6),

6.3 季度增量合并的两阶段流程

阶段一：草稿期（自动化）

  • 季度运行结束后，将所有记录写入 extraction_draft 表，status='pending'。
  • 生成 增量报告 xlsx（一份Sheet对应一张事实表）发往审核队列。

阶段二：人工确认期（人工）

  • 数据审核员在 Web 工作台勾选：
  • Approve → 调用 MergeService.merge(record_id)：
    • 计算 record_id + literature_id 指纹
    • 若主表存在同 lit+mode+region+year 的记录 → 选择"覆盖 / 跳过 / 合并"
    • 默认策略：lit 唯一则追加；重复则保留更新时间最新者
  • Reject → 草稿状态置 rejected 并记录原因
  • Edit → 进入字段编辑器（双栏：原文 / 字段值）

审计字段（每张事实表必备）：

merged_by   TEXT,
merged_at   TIMESTAMPTZ,
merger_version TEXT,         -- merge_strategy 的版本号
evidence_blob BYTEA,         -- 来自原文 evidence_text+page

6.4 与现有 xlsx 的兼容

现有 11 个工作表 ⇒ 一次性反向 ETL 入新库（一次性脚本），生成 legacy_xlsx_audit 报告，列出： - 重名字段（如 "硝氮" 与 "硝酸盐氮"） - 单位散乱（如"kg/亩"与"kg/m³"并存的产量列） - 经纬度空值（占 39%）

后续主表 schema 与 xlsx 影子对比： - 每周五自动导出 xlsx 镜像 - 每月 1 日对账两张表的关键指标 hash

7. 季度自动化执行流程

7.1 调度（Cron 编排）

主调度任务用 Apache Airflow（企业级首选）或 Celery Beat（轻量级够用）二选一。

# DAG / 周期任务 调度 上游依赖 SLA
1 lit_search_quarterly（季度检索） 0 2 1 */3 * — 6h
2 lit_fetch_fulltext（全文获取） 由 1 触发 1 成功 24h
3 lit_extract（解析+抽取） 由 2 触发 2 成功 36h
4 data_quality_check（质控） 由 3 触发 3 成功 4h
5 human_review_queue（推送审核） 由 4 触发 4 完成 —
6 merge_to_main（合并入主表） 由 5 + 人工 Approve — —
7 quarterly_report_export（导出报告） 0 22 28-31 */3 * 1-6 全完成 2h
8 db_health_backup（备份） 每日 — —

7.2 季度执行 Runbook

D 日：00:00 调度器启动检索
  ├─ 02:00 完成 32 query × 6 源 = 192 个调用（自适应并发 ≤ 6）
  └─ 06:00 全文抓取（比例：英文 ≤ 80%、中文摘要 100%）
D+1 日：08:00 解析+抽取
  ├─ 14:00 抽取完成；草稿表落库
  └─ 16:00 质控报告
D+2 日：~ 数据审核员 Review
  ├─ APPROVE → MergeService 入主表
  └─ REJECT/EDIT → 反馈循环
D+2 末日 23:00：批次封板，落季度归档快照

7.3 失败兜底

  • 任一 DAG 任务 3 次自动重试失败 → 写入 Dead Letter Queue（DLQ）。
  • DLQ 在工作台"异常队列"页面可手动重跑或回退版本。
  • 人工通知：钉钉/飞书机器人推送失败 Summary。
