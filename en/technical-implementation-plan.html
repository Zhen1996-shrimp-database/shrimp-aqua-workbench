3.2 Step 6: 文档解析双引擎

引擎 用途 关键能力
PyMuPDF (fitz) 学术 PDF 默认首选项 快, 坐标精确, 表格框选

3.3 Step 7-9: 字段Extract = "规则 + LLM" 双通道

通道 A: 规则Extract (首选)

针对高频模板的论文 (中国海洋大学博论文 / 期刊固定栏目): - 训练 CRF/正则匹配置信度 ≥ 0.9 时直接采纳. - 例: r"survival rate.*?(\d+(?:\.\d+)?)\s*%" - 例: r"Feed conversion ratio[为:为可低]?\s*(\d+(?:\.\d+)?)"

通道 B: LLM extraction (兜底)

SYSTEM:
你是水产养殖数据Extract专家.每次给出 JSON, 禁止输出解释.
Extract字段集合 (schema 注入, 禁止越界): 
  water_quality: {Water temperatureWT, pH, DO, Salinity, NH3-N, NO2-N, NO3-N, COD, TN, TP,
                  Transparency, 总碱度, 钙离子}
  cost_items: {苗种, Feed, Animal health, Labor, 租金, Water & electricity, Equipment折旧}
  benefit: {单产, 总产, 产值, Net profit, InputOutput比, ROI, FCR, 成活率}
  meta: {Farming mode, culture cycle, Seedling release密度, Size, 地域, Time, 文献Source}

USER:
[Source片段 chunk N of M] (含页码/表格编号)
请输出 JSON.每个字段都给出 evidence_text 与 page_no.
找不到则留 null 并NotesMissing原因.

约束: 
- Value必须与Source一致, 禁止换算
- 含义不明时给 ""unknown""
- 单records只对应同一篇文献同一组数据
- 不要把Unit写成数字的一部分

两通道融合规则: 1. 规则先跑; Hit且置信度 > 0.9 → 直接采纳. 2. 未Hit字段 → 调用 LLM. 3. LLM extraction与规则一致 → 二者皆入库 (投票机制). 4. 二者冲突 → 进 L2 Labor核验队列.

3.5 ExtractFailed兜底

  • 若文献无可用全文 → 仅入库"文献实体表", 不入数据表, 标 fulltext=missing.
  • 若 OCR failed 3 次 → Escalate transcription queue.
  • 若 LLM 调用超时 / token 超限 → 分 chunk 重试 + 异步Merge.

4. Duplicate paper deduplication机制

采用 "指纹 + Text相似度" Three-stage funnel, 3 分钟内处理 1 万records.

4.1 三级Dedup漏斗

输入记录
   │
   ▼
Level 1 — DOI / PMID / CN号 Exact match Hit → 跳过
   │ 未Hit
   ▼
Level 2 — Title指纹 (SimHash 64-bit / MinHash) 汉明距离 ≤ 3 → 提示Merge
   │ 未Hit
   ▼
Level 3 — 嵌入向量召回 (pgvector, text-embedding-3-small)
          + cosineThreshold 0.93 → EnterLaborMerge决策 未Hit → 入新记录

4.2 Level 1 Exact match

SELECT id FROM literature
WHERE doi = ?
   OR (pmid IS NOT NULL AND pmid = ?)
   OR (cn_no IS NOT NULL AND cn_no = ?);

4.3 Level 2 Title指纹

  • 预处理: 去标点 → 转小写 → 去前后空格 → 中文用 jieba 分词 + 英文用 NLTK 词形还原.
  • Hash: SimHash 64bit (也可切 MinHash-128 用于候选召回).
  • Hit: 汉明距离 ≤ 3 或 Jaccard ≥ 0.85.

4.4 Level 3 嵌入向量

索引 推荐 维度
pgvector + HNSW 默认 1536
备选 Qdrant + IVF 大规模 1536 
CREATE TABLE lit_embedding (
  lit_id BIGINT PRIMARY KEY,
  embedding vector(1536) NOT NULL
);
CREATE INDEX lit_embedding_hnsw ON lit_embedding
USING hnsw (embedding vector_cosine_ops);

4.5 Merge策略

情况 行为
同一文献在不同数据库 (CNKI 与 WoS 各有一records) Merge为一条, 由"主源"承载元数据, Other源写进 duplicate_of
同一数据集在不同期刊发表的姊妹篇 保留两条, 标记 related_paper_of
同一数据被多次引用 每条Extract独立入库, 文献实体的 cited_by_records 反查计数

5. Data-quality validation规则

5.1 Validation rules引擎架构

采用 Great Expectations + Soda Core 双核:

  • GE: schema, 强Type, 范围, 跨表一致性.
  • Soda: Custom业务规则 (典型: CostShareTotal = 100%).

所有规则代码入库 data-quality/rules/, rule-as-code, 每次 ETL 自动跑.

5.2 12 类规则全景

# 类别 规则示例 Failed处理
R01 完整性 必填字段非空: source_id, doi/title, literature_id, year Severe → 拒收; 非Severe → 进补全队列
R02 唯一性 literature_id 主键唯一; 草稿表内 lit_id + section_no 唯一 拒收
R03 ValueType WT, DO, pH 等必须是 float; 不可夹杂Unit字符串 解析前清洗
R04 范围 sanity check WT ∈ [5, 40]°C; DO ∈ [0, 20] mg/L; pH ∈ [5, 11]; Salinity ∈ [0, 50]‰; NH₃-N ∈ [0, 50] mg/L 警示 + 进Labor核对
R05 逻辑一致性 Seedling release密度 × 养成Size × 周期 → 总产应满足密度约束; 溶解氧 < 0 时 FCR 必有显著偏高 警示
R06 比例约束 Cost分项ShareTotal = 100% ± 0.5%; 若是± 5% 进差异队列 警示 + 重核
R07 Unit一致 mg/L μg/L g/m³ 自动归一, Unit跟随默认 Auto-convert
R08 货币Time归一 Price → 2025 基准 CPI 折算; 汇率取人民银行年中值 自动
R09 跨表交叉验证 Water quality表 vs Growth表: 同一 lit_id + culture_mode 的 WT 偏差 > 3°C 必查 警示
R10 Source可追溯 每条Extract记录必含 evidence_text + page_no + extraction_prompt_ver 拒收
R11 Latitude / longitude一致性 同一SiteLatitude / longitude偏差 > 0.2° → 提示; 省份与经纬反查行政编码不一致则Blocked Blocked
R12 可重复性 同一篇文献二次Extract结果差异 > 5% 字段 → 进配置巡检 提示

5.3 校验Failed的分级处置

PASS ─ 入主库 L1
WARN ─ 入主库 L2 (黄色标), 触发邮件给数据管理员
BLOCKED ─ 仅入草稿 + Review 队列, 需Labor确认
CRITICAL ─ 自动告警到飞书/钉钉群 + 创建 Jira

);

6.3 季度增量Merge的两阶段流程

阶段一: 草稿期 (自动化)

  • 季度运行结束后, 将所有记录写入 extraction_draft 表, status='pending'.
  • 生成 增量报告 xlsx (一份Sheet对应一张事实表)发往审核队列.

阶段二: Labor确认期 (Labor)

  • Data review员在 Web 工作台勾选:
  • Approve → 调用 MergeService.merge(record_id):
    • 计算 record_id + literature_id 指纹
    • 若主表存在同 lit+mode+region+year 的记录 → 选择"覆盖 / 跳过 / Merge"
    • 默认策略: lit 唯一则追加; 重复则保留更新Time最新者
  • Reject → 草稿状态置 rejected 并记录原因
  • Edit → Enter字段编辑器 (双栏: Source / 字段值)

审计字段 (每张事实表必备): 

merged_by TEXT,
merged_at TIMESTAMPTZ,
merger_version TEXT, -- merge_strategy 的版本号
evidence_blob BYTEA, -- 来自Source evidence_text+page

6.4 与现有 xlsx 的兼容

现有 11 个Worksheet ⇒ 一次性反向 ETL 入新库 (一次性脚本), 生成 legacy_xlsx_audit 报告, 列出: - 重名字段 (如 "Nitrate-N" 与 "Nitrate nitrogen") - Unit散乱 (如"kg/亩"与"kg/m³"并存的产量列) - Latitude / longitude空value (占 39%)

后续主表 schema 与 xlsx 影子对比: - 每周五自动Export xlsx 镜像 - 每月 1 日对账两张表的关键Indicator hash

7. 季度自动化执行流程

7.1 调度 (Cron 编排)

主调度任务用 Apache Airflow (企业级首选)或 Celery Beat (轻量级够用)二选一.

# DAG / 周期任务 调度 上游依赖 SLA
1 lit_search_quarterly (季度检索) 0 2 1 */3 * — 6h
2 lit_fetch_fulltext (全文获取) 由 1 触发 1 成功 24h
3 lit_extract (解析+Extract) 由 2 触发 2 成功 36h
4 data_quality_check (QC) 由 3 触发 3 成功 4h
5 human_review_queue (推送审核) 由 4 触发 4 完成 —
6 merge_to_main (Merge入主表) 由 5 + Labor Approve — —
7 quarterly_report_export (Export报告) 0 22 28-31 */3 * 1-6 全完成 2h
8 db_health_backup (备份) 每日 — —

7.2 季度执行 Runbook

D 日: 00:00 调度器启动检索
  ├─ 02:00 完成 32 query × 6 源 = 192 个调用 (自适应并发 ≤ 6)
  └─ 06:00 全文抓取 (比例: 英文 ≤ 80%, 中文摘要 100%)
D+1 日: 08:00 解析+Extract
  ├─ 14:00 Extract完成; 草稿表落库
  └─ 16:00 QC report
D+2 日: ~ Data review员 Review
  ├─ APPROVE → MergeService 入主表
  └─ REJECT/EDIT → 反馈循环
D+2 末日 23:00: Batch封板, 落季度归档快照

7.3 Failed兜底

  • 任一 DAG 任务 3 次自动重试failed → 写入 Dead Letter Queue (DLQ).
  • DLQ 在工作台"Anomaly队列"页面可手动重跑或回退版本.
  • Labor通知: 钉钉/飞书机器人推送failed Summary.
